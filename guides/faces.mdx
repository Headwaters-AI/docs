# Faces

A face is a named persona — a compiled character that can be used as the system personality for any chat completion. Faces are identified by a unique `alias` within your account.

---

## Create a face

```bash
curl -X POST https://api.faces.sh/v1/faces \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "alias": "alice",
    "name": "Alice",
    "description": "Senior product designer based in Berlin.",
    "basic_facts": {"age": "30", "location": "Berlin"}
  }'
```

### Alias rules

- Lowercase letters, numbers, and dashes only: `^[a-z0-9-]+$`
- Maximum 32 characters
- Must be unique within your account

### `description`

Optional plain-text bio (up to **1500 characters**, roughly 200–250 words). Useful for a human-readable summary of who this face is — not used by the model at inference time, but surfaced in listings and dashboards.

- Plain text. HTML is stored verbatim; if you render it, escape it yourself.
- Server strips ASCII control characters and normalizes line endings.
- Send `"description": ""` to clear it. Omit the field on PATCH to leave it unchanged.

### `basic_facts`

A key:value object injected into the system prompt on every chat request. Use it for facts that should always be present regardless of compiled context: name, role, location, key relationships.

```json
{"age": "30", "location": "Berlin", "role": "product designer"}
```

Only keys from the [supported attributes list](#list-supported-attributes) are accepted. Unsupported keys are dropped and a `warnings` array is included in the response indicating which keys were removed.

### `profile_addendum`

A saved system prompt fragment stored on the face. It is prepended to every inference request the face receives. Unlike `description` — which is human-facing metadata that never reaches the model — `profile_addendum` **is** sent to the model on each chat request.

Use it for durable behavioral instructions: output format rules, guardrails, tone constraints, tool-use conventions.

```bash
curl -X POST https://api.faces.sh/v1/faces \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "alias": "support-bot",
    "name": "Support Bot",
    "profile_addendum": "Always answer in under 3 sentences. Never promise refunds.",
    "default_model": "claude-sonnet-4-6"
  }'
```

- **Maximum 100,000 characters.** Over the limit returns `422`. Formatting (blank lines, indentation) is preserved; ASCII control characters are stripped.
- Applies on **all** inference endpoints — `/v1/chat/completions`, `/v1/messages`, and `/v1/responses`.
- Send `"profile_addendum": ""` to clear it. Omit the field on PATCH to leave it unchanged.
- Returned on `GET /v1/faces/{alias}` **only for the face's owner**. It is treated as proprietary (like the persona) and is never exposed on cross-user or [published](/guides/system-faces) face listings, nor echoed back in `/v1/responses` output.
- For [synthetic faces](/guides/synthetic-faces): a persisted composite uses its own `profile_addendum`; a run-time composite borrows the **first operand's**.

## List faces

```bash
curl https://api.faces.sh/v1/faces \
  -H "Authorization: Bearer YOUR_API_KEY"
```

Each face item always includes `description`. By default, `tags`, `teams`, and the compiled-profile fields are returned as `null` — opt in with `?include=` (repeatable or comma-separated). Recognized values: `tags`, `teams`, `profile`.

```bash
# Tags + teams + the five compiled-profile fields on every item
curl "https://api.faces.sh/v1/faces?include=tags,teams,profile" \
  -H "Authorization: Bearer YOUR_API_KEY"
```

```json
{
  "object": "list",
  "data": [
    {
      "alias": "alice",
      "uid": "...",
      "description": "Senior product designer based in Berlin.",
      "tags": ["client:acme", "status:active"],
      "teams": [
        {"id": "...", "name": "Platform Engineering"}
      ],
      "default_model": "gpt-4o-mini",
      "profile_token_count": 712,
      "total_tokens_saved": 84210,
      "component_counts": [18, 22, 11, 6, 3],
      "compile_tokens_synced": 8200,
      "last_synced_at": "2026-04-22T16:24:05.932712",
      "...": "..."
    }
  ]
}
```

`?include=profile` populates five fields in one round-trip — designed for table-style face listings (dashboard rows, CLI tables) so you don't have to pair `GET /v1/faces` with `GET /v1/faces/stats` and merge client-side. The same five field names appear on `GET /v1/faces/stats` for high-frequency polling, and on `GET /v1/faces/{alias}?include=profile` for single-face reads.

| Field | Meaning |
| --- | --- |
| `profile_token_count` | Tokens in the compiled persona prompt rendered from this face. |
| `total_tokens_saved` | Cumulative LLM tokens this face's compiled profile has avoided sending. |
| `component_counts` | How many components of each kind the face currently has. See below. |
| `compile_tokens_synced` | Tokens of source content currently synced into the graph. Decrements when sources are deleted. |
| `last_synced_at` | ISO timestamp of the most recent compile sync, or `null` if the face has never been synced. |

### Component counts

`component_counts` is an array of numbers — a count per kind of component, in a fixed
order:

```json
"component_counts": [18, 22, 11, 6, 3]
```

Sum it for a total. Read it positionally if you want the breakdown: position N always
means the same kind, positions are never reordered or removed, and new kinds are
appended to the end. Read it by iterating rather than assuming a length, and a future
addition cannot break you.

A face that has never compiled returns zeros rather than `null`, so a renderer needs
no special case. The field itself is only present when requested with `?include=profile`.


The list endpoint also accepts two filter parameters that compose:

- `?tag=` — repeatable. Multiple tags use **AND** (face must carry every listed tag). Values are lowercased before match.
- `?team_id=` — repeatable. Multiple team_ids use **OR** (face must be a member of *any* listed team).

The two combine as `(tag1 AND tag2) ∩ (team1 OR team2)`:

```bash
# Faces tagged client:acme that are members of either team T1 or team T2
curl "https://api.faces.sh/v1/faces?tag=client:acme&team_id=T1&team_id=T2" \
  -H "Authorization: Bearer YOUR_API_KEY"
```

`?team_id=` values that don't exist (or that match a team with no members) return zero matches without an error. Unknown values in `?include=` are silently ignored.

### Include published (system) faces

By default the list returns only faces you own. Pass `?include_published=true` to also include faces published system-wide — the [system faces](/guides/system-faces) under the `head` account, and any face another account has chosen to publish. Each published item has `published: true` and an `owned_by` you combine into the chat handle `owned_by:alias` (e.g. `head:maestro`).

To see faces made available to **you specifically** rather than to everybody, pass `?include_shared=true`. The two are independent and neither implies the other — see [Sharing Faces](/guides/sharing).

```bash
# Your own faces plus all published system faces
curl "https://api.faces.sh/v1/faces?include_published=true" \
  -H "Authorization: Bearer YOUR_API_KEY"

# Only the system faces from the head account
curl "https://api.faces.sh/v1/faces?include_published=true&from_users=head" \
  -H "Authorization: Bearer YOUR_API_KEY"
```

Two optional owner filters narrow the published results (they apply only to published faces, not your own):

- `?from_users=` — **allowlist**, repeatable or comma-separated. Only published faces owned by these accounts are returned.
- `?not_from_users=` — **blocklist**, repeatable or comma-separated. Published faces owned by these accounts are excluded.

`from_users` and `not_from_users` are mutually exclusive — passing both returns **`400`**. The tag and team filters apply to owned faces only.

## Get a face

```bash
curl https://api.faces.sh/v1/faces/FACE_ALIAS \
  -H "Authorization: Bearer YOUR_API_KEY"
```

`description` is always populated. `tags`, `teams`, and the five compiled-profile fields (`profile_token_count`, `total_tokens_saved`, `component_counts`, `compile_tokens_synced`, `last_synced_at`) are `null` unless requested via `?include=`:

```bash
curl "https://api.faces.sh/v1/faces/FACE_ALIAS?include=tags,teams,profile" \
  -H "Authorization: Bearer YOUR_API_KEY"
```

## Update a face

```bash
curl -X PATCH https://api.faces.sh/v1/faces/FACE_ALIAS \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "basic_facts": {"age": "30", "location": "Berlin", "role": "senior product designer"},
    "default_model": "gpt-4o-mini"
  }'
```

### `default_model`

Sets the LLM used when no model is specified in the chat request. Accepts any model name from the [supported models list](/api-reference/openapi). Leave null to use the system default.

PATCH also accepts `description`, `profile_addendum`, `formula`, `basic_facts`, `default_tools`, and `name`. For the text fields (`description`, `profile_addendum`) an empty string clears the field and omitting it leaves it unchanged.

## Lock a face

Locking a face freezes it. While locked, the face and everything it owns can still be **read and chatted with**, but **nothing can be changed** — every write is refused. Use it to protect a face you don't want edited.

Toggle the lock with a single call (owner only):

```bash
# Lock
curl -X PATCH https://api.faces.sh/v1/faces/FACE_ALIAS/lock \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"read_only": true}'

# Unlock
curl -X PATCH https://api.faces.sh/v1/faces/FACE_ALIAS/lock \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"read_only": false}'
```

```json
{ "alias": "FACE_ALIAS", "read_only": true, "affected": ["FACE_ALIAS"] }
```

Every face response (single and list) includes a `read_only` boolean, defaulting to `false`, so you can read the current state without toggling. `affected` lists the aliases whose state changed — everything belonging to the face freezes and thaws together.

### What a lock blocks

When a face is locked, any write to it or to anything it owns is refused with `409`:

| Blocked while locked | Still allowed |
|----------------------|---------------|
| Editing the face — name, description, basic facts, model, and the rest | Reading the face, its documents, and its threads |
| Adding, editing, compiling, or deleting its documents and threads | Chatting with the face (inference) |
| Uploading or importing new source material | Unlocking it |
| Deleting the face itself | |

To delete a locked face, unlock it first — unlocking is the one change a locked face always accepts.

## Delete a face

```bash
curl -X DELETE https://api.faces.sh/v1/faces/FACE_ALIAS \
  -H "Authorization: Bearer YOUR_API_KEY"
```

Deleting a face removes everything compiled from it, and it stops appearing in [centroid index](/concepts/centroids) results. Documents compiled exclusively for this face are also removed.

## Tags

Lightweight lowercase labels attached directly to a face. Use them for quick grouping and filtered search — for example `client:acme`, `status:active`, or `release-candidate`.

### Rules

- Pattern: `^[a-z0-9][a-z0-9:\-_.]{0,63}$`
- Lowercase only, max 64 chars, no spaces
- Namespacing via `:` is encouraged (`client:acme`, `team:platform`)
- Max 32 tags per face
- Duplicates are collapsed silently

Only the face's owner can edit its tags.

<Note>
**Tags are a face-level concept.** All `/v1/iam/{id}/tags` endpoints require the target to be a face. Passing a user account's username or UID returns **`400`** with the message *"Tags are only supported on faces."* If a username is shared between a user account and a face (allowed — usernames are not unique across IAM types), the face is preferred automatically. To be unambiguous, pass the face's UID.
</Note>

### Replace all tags

```bash
curl -X PUT https://api.faces.sh/v1/iam/FACE_UID/tags \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"tags": ["client:acme", "status:active"]}'
```

### Add one or more tags (idempotent)

```bash
curl -X POST https://api.faces.sh/v1/iam/FACE_UID/tags \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"tags": ["urgent"]}'
```

### Remove a single tag

URL-encode the tag in the path (`:` becomes `%3A`):

```bash
curl -X DELETE "https://api.faces.sh/v1/iam/FACE_UID/tags/client%3Aacme" \
  -H "Authorization: Bearer YOUR_API_KEY"
```

### List tags on a face

```bash
curl https://api.faces.sh/v1/iam/FACE_UID/tags \
  -H "Authorization: Bearer YOUR_API_KEY"
```

### List all tags across your faces

For tag-picker overlays and similar UIs, fetch the union of every tag across the faces you own:

```bash
curl https://api.faces.sh/v1/me/tags \
  -H "Authorization: Bearer YOUR_API_KEY"
```

```json
{ "tags": ["client:acme", "release-candidate", "status:active", "urgent"] }
```

Sorted, deduped, lowercase. Cheap to call — fetches only the tag predicate across owned faces, no other data.

### Filter the face list by tags

`GET /v1/faces` accepts a repeated `?tag=` query parameter. Multiple tags are combined with **AND** — only faces that carry every listed tag are returned. See [List faces](#list-faces) for composition with `?team_id=` and the `?include=` enrichment flag.

```bash
# All faces tagged client:acme
curl "https://api.faces.sh/v1/faces?tag=client:acme" \
  -H "Authorization: Bearer YOUR_API_KEY"

# Intersection: both tags required
curl "https://api.faces.sh/v1/faces?tag=client:acme&tag=urgent" \
  -H "Authorization: Bearer YOUR_API_KEY"
```

## Team membership

Replace a face's team-membership list in one call. Idempotent — sending the same body twice is a no-op.

```bash
curl -X PUT https://api.faces.sh/v1/faces/FACE_ALIAS/teams \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"team_ids": ["TEAM_UID_1", "TEAM_UID_2"]}'
```

```json
{
  "teams": [
    {"id": "TEAM_UID_1", "name": "Platform Engineering"},
    {"id": "TEAM_UID_2", "name": "Acme Project"}
  ]
}
```

The body's `team_ids` becomes the face's complete membership list — extras get added, missing ones get removed. Send `{"team_ids": []}` to clear all memberships.

### Authorization

| Case | Status |
| --- | --- |
| Caller doesn't own the face | `404` (or `403` if the face exists but isn't owned by the caller) |
| Listed team_id doesn't exist | `400` |
| Caller doesn't manage one of the listed teams | `403` |
| Removing the face from a team the caller doesn't manage | allowed — the face owner has full control over their face's memberships |

The asymmetry on removals mirrors `DELETE /v1/teams/{id}/members/{iam}`: a member's owner can take their face out of any team they're in, but adding to a team always requires the team's manager.

## Upload source texts

Upload documents, transcripts, or threads to be compiled into the face.

```bash
# Text, PDF, or Word document
curl -X POST https://api.faces.sh/v1/faces/alice/upload \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -F "file=@interview.docx" \
  -F "type=document"

# Pre-written transcript (plain text)
curl -X POST https://api.faces.sh/v1/faces/alice/upload \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -F "file=@transcript.txt" \
  -F "type=thread"
```

### Supported file types

| Type | Formats |
|------|---------|
| Document | `.txt`, `.md`, `.csv`, `.json`, `.jsonl`, `.xml`, `.html`, `.rst`, `.pdf`, `.docx` |
| Thread | `.txt` (structured transcript) |
| Audio/Video | `.mp3`, `.mp4`, `.wav`, `.m4a`, `.webm`, and more |

Word (`.docx`) and PDF files have their text extracted for you — upload the file as
it is, no conversion needed.

Audio and video files are transcribed asynchronously — the upload returns **202** with `prepare_status: "transcribing"`. Poll the thread or document GET endpoint until `prepare_status` becomes `null` (ready to review) or `"failed"`. Text, PDF, and Word uploads return 200 synchronously.

To get the raw transcript without creating a compile thread/document, use the `/transcribe` endpoint instead.

#### Word documents

Paragraph order is preserved, along with the blank lines between paragraphs and any
tabs or line breaks inside one — so a transcript that uses tabs to mark who is
speaking keeps its shape. Table cells are read in document order.

Only document text is read. Images and text boxes are ignored, so a `.docx` that is
just a scanned page arrives empty and is rejected with `422`.

| If the file is | You get | What to do |
|----------------|---------|------------|
| a legacy `.doc` | `400` | Open it in Word or Pages and save as `.docx` |
| password-protected or corrupt | `400` | Remove the password and upload again |
| a `.docx` with no text in it | `422` | Check the file — images and text boxes are not read |

A `400` means the file itself is wrong and a different file is needed. A `422` means
the file was read fine and had nothing in it. Neither is worth retrying as-is.

## Import

Import a public URL — the content is fetched, transcribed if needed, and stored as a document or thread. Returns **202** immediately; transcription runs in the background.

```bash
curl -X POST https://api.faces.sh/v1/faces/alice/import \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"url": "https://www.youtube.com/watch?v=VIDEO_ID"}'
# Returns 202 with prepare_status="transcribing"
# Poll GET /v1/compile/documents/{id} or /v1/compile/threads/{id} until ready
```

## Transcribe audio/video

Transcribe without compiling. Returns raw text and speaker-diarized segments:

```bash
curl -X POST https://api.faces.sh/v1/faces/alice/transcribe \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -F "file=@podcast.mp3"
```

```json
{
  "data": {
    "text": "Full transcript text...",
    "segments": [
      { "speaker": "A", "start": 0.0, "end": 4.2, "text": "Welcome to the show." },
      { "speaker": "B", "start": 4.5, "end": 8.1, "text": "Thanks for having me." }
    ]
  }
}
```

Transcription is billed separately from compile quota. See [Billing guide](/guides/billing).
