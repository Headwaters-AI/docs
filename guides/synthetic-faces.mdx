# Synthetic Faces

A synthetic face is defined by a boolean formula over existing faces. It is assembled on the fly — no separate compilation, no extra training. The formula is evaluated at inference time by taking the union, intersection, or difference of the contributing faces' compiled material.

---

## Formula syntax

| Operator | Meaning |
|----------|---------|
| `a \| b` | Union — everything from a and everything from b |
| `a & b` | Intersection — only what a and b share |
| `a - b` | Difference — everything from a that is not in b |
| `a ^ b` | Symmetric difference — everything unique to either a or b |

Parentheses are supported for grouping:

```
(alice | bob) & mentor
alice | (expert - academic)
```

---

## Create a synthetic face

Pass a `formula` instead of uploading documents:

```bash
curl -X POST https://api.faces.sh/v1/faces \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "alias": "alice-and-bob",
    "formula": "alice | bob"
  }'
```

The formula references faces by their `alias`. All referenced faces must:
- Be owned by you
- Be concrete (non-synthetic) faces

Nesting synthetic faces — referencing a face that itself has a formula — is not supported and returns `422`.

---

## Update the formula

```bash
curl -X PATCH https://api.faces.sh/v1/faces/FACE_ALIAS \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"formula": "alice & mentor"}'
```

Changes take effect immediately on the next chat request.

---

## Chat with a synthetic face

Exactly the same as chatting with any face:

```bash
curl -X POST https://api.faces.sh/v1/chat/completions \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "alice-and-bob",
    "messages": [{"role": "user", "content": "How do you approach creative problems?"}]
  }'
```

---

## Validation rules

- All referenced aliases must be owned by you at create/update time.
- Referenced faces must be concrete (not synthetic themselves).
- The formula must be a valid boolean expression using `|`, `&`, `-`, `^`, parentheses, and valid aliases.

Invalid formulas return `422` with a description of the problem.

---

## How it works

When a chat request arrives for a synthetic face, the profiler service:

1. Evaluates the formula, reading the compiled material for each referenced face.
2. Applies the boolean operations to produce a merged knowledge set.
3. Retrieves and ranks the most relevant material from the merged set.
4. Injects them into the system prompt as if they were compiled for a single face.

The result is a coherent persona that blends the source faces according to the formula — without any training or separate compilation step.

---

## Use cases

- **Blended expertise**: `designer | engineer` — draw on both knowledge domains in a single persona.
- **Constrained character**: `alice & mentor` — only the sides of Alice that also read as a mentor.
- **Differenced persona**: `senior-dev - junior-dev` — the characteristics that distinguish a senior developer from a junior one.
- **A/B testing**: Create `alice | bob` and `alice & bob` to compare unioned vs. intersected personas.

## Run-time composites (compose on the fly)

You don't have to create a synthetic face first. You can pass a formula **directly in the `model` field** of a chat request and have it composed for that one call:

```bash
curl -X POST https://api.faces.sh/v1/chat/completions \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "(alice | bob)@claude-sonnet-4-6",
    "messages": [{"role": "user", "content": "How do you approach creative problems?"}]
  }'
```

The same operators apply (`|`, `&`, `-`, `^`, parentheses). This works on all three inference endpoints — `/v1/chat/completions`, `/v1/messages`, and `/v1/responses`.

Behaviorally a run-time composite is identical to a persisted one of the same operands — the knowledge is merged the same way, from the operands' cached knowledge, so there's no meaningful latency difference. The choice is ergonomic: persist when you'll reuse it (and want to name it); compose on the fly for one-off blends.

### Rules

- **An explicit `@model` is required.** A run-time composite has no stored `default_model`, so the bare form `(alice | bob)` (no `@model`) returns `400`. Persisted synthetic faces, by contrast, can carry a `default_model`.
- **Operands must be your own concrete faces** — same as persisted formulas. Unknown/unowned operand → `404`; referencing a synthetic face as an operand → `422` (no nesting).
- **`owner:alias` operands are not supported** inside a run-time formula — operands are your own faces by bare alias. (Use a persisted synthetic face if you need something more elaborate.)
- **Difference needs spaces:** write `alice - bob` (a dash *between* characters, like `news-bot`, is read as part of an alias). This matches persisted-formula behavior.

### Identity: the first operand

A composite needs a single identity to embody. A run-time composite takes its **name and any [`profile_addendum`](/guides/faces#profile-addendum) from the first (leftmost) operand**. This is consistent with the union precedence — in `a | b`, operand `a` wins on conflicts, so it's the natural identity anchor:

```
(alice | bob)@model   →  embodies "Alice", augmented with Bob's knowledge
(bob | alice)@model   →  embodies "Bob", augmented with Alice's knowledge
```

If you want a **custom** name or system prompt for the blend (rather than inheriting the first operand's), create a persisted synthetic face — you name it and set its `profile_addendum` at creation.
